# Auto-Dev Agent 设计文档

## 1. 目标与定位

Auto-Dev Agent 是面向业务代码仓库的自主研发、排障与修复代理系统。系统接收自然语言需求或报错描述，先在入口区分故障修复（`bugfix`）、功能创建（`feature`）与只读诊断问答（`qa`）意图并按需收集上下文证据，再于隔离的 Linux 容器沙箱中完成代码生成/修改、测试验证与自愈，最后经人工确认提交 Git 变更（只读诊断类请求则在取证分析后直接收束输出，不进入改码审批）。

设计上融合两个参考项目的核心能力：

| 参考项目 | 吸收机制 | 在本项目的落地点 |
|---|---|---|
| my_swe | 分层结构、证据收集与双路缓存 | clients/deps/repos 分层、DatasourceRegistry、evidence_collector、ES+Qdrant 报错缓存、Send 并行探查、Linux 容器沙箱 |
| aider | 仓库理解与代码修改闭环 | Tree-sitter + PageRank RepoMap、SEARCH/REPLACE 精准编辑、Git 提交回滚、前缀缓存分层 |

## 2. 核心设计约束

### 2.1 测试代码隔离

- `services` 层严禁出现任何测试逻辑、故障造数、Mock 分支或测试开关。
- `services` 层严禁出现硬编码路径、硬编码账号、写死的项目 ID 或兜底示例数据。
- 所有测试初始化数据统一收口到独立模块 `app/seed/`，仅在部署初始化或独立测试脚本中调用，业务主链路不可反向依赖 `app/seed/`。

**决策理由**：避免业务逻辑与演示/测试数据耦合，确保生产服务与测试数据单向解耦，降低后续替换真实业务仓库时的改造成本。

### 2.2 入口意图分流与四类上下文/证据来源

系统根据 `user_query` 与数据源信号做入口意图分流（`bugfix` / `feature` / `qa`），按需启用以下只读探针：

| 证据类型 | 标识 | 探查方式 | 触发条件 |
|---|---|---|---|
| 数据库查询 | `db_query` | 对用户接入的数据源执行只读 SQL 查询与 Schema 探测 | 仅当用户配置了数据库数据源且当前意图需要（`bugfix` / `feature` / 涉库 `qa`） |
| 日志报错 | `log_error` | 优先直读用户配置的 ES 日志索引；未配置 ES 时降级扫描本地日志文件 | `bugfix` 默认启用；`qa` 在传入日志线索时启用；纯 `feature` 创建跳过 |
| 报错缓存 | `error_cache` | ES (BM25) + Qdrant (向量) RRF 混合检索历史报错 Runbook | `bugfix` 默认启用；`qa` 涉报错时启用；纯 `feature` 创建跳过 |
| 源码分析 | `source_code` | 由模型结合 `RepoMap` 与只读工具（`ls_directory` / `grep_code` / `read_file_window` / `git_log_recent`）自主多轮探索，并将已读文件纳入 `chat_fnames` | 始终启用（无有效 LLM Key 时降级为确定性检索） |

- 用户可通过接口或任务参数接入外部数据源。
- 若用户未指定数据源，系统不初始化数据库连接，证据探查子图自动跳过 `db_query`，不报错也不退化为硬编码库。
- **日志探针降级规则**：若用户配置了 ES 日志索引，日志探针直接查询 ES；未配置 ES 时，自动降级为只读扫描任务指定的 `log_path` 或工作区内 `*.log` 文件；两者均无可用日志时记录 `gaps` 并继续主流程。
- **报错缓存加速与统一采集**：直接复用 `my_swe` 的 `evidence_collector` 模块与报错经验缓存机制。所有探查工具返回内容统一经 `redact_text` 脱敏并由 `build_evidence` 签发唯一编号（`ev_db:` / `ev_log:` / `ev_code:` / `ev_cache:`）。

**决策理由**：避免“新增功能”白跑报错日志检索，也避免“只读日志/源码问答”误进改码沙箱；同时通过模型自主调度源码工具与统一证据签发，防止在未确认既有代码结构前凭空生成或泄露敏感凭证。

### 2.3 双子图隔离执行

系统将核心工作流拆分为两个独立子图：

1. **证据探查子图**：负责多源证据收集与去重，子图内各探针的中间工具调用消息在出子图时回收，仅将标准化 `Evidence` 列表写回主图。
2. **Linux 容器沙箱子图**：负责在独立 Linux 容器中同步代码修改、运行 lint 与单元测试并执行自愈重试，隔离宿主环境与测试副作用。

**决策理由**：隔离探查过程与沙箱运行过程产生的大量工具调用上下文，防止主图状态膨胀，同时隔离大模型生成代码在宿主机直接执行的风险。

## 3. 核心业务流程

1. 用户提交研发、修复或诊断任务，可选择绑定项目工作区、外部数据源及 `log_path`。
2. 系统通过持久化 `RepoMapManager` 生成或更新 `RepoMap` 代码大纲，并由 `intent_router` 判定任务意图（`bugfix` / `feature` / `qa`）与启用的探针清单。
3. 进入**证据探查子图**，按启用清单并发调度对应探针；其中 `code_probe_worker`（代码 ReAct）与 `db_probe_worker`（数据库 ReAct，挂载 DB 数据源时启用）分别由模型结合 `RepoMap` / `DBRepoMap`（PageRank 库表拓扑与外键关系）自主调用只读工具读取关键源码、验证表结构并运行只读 `SELECT` 查错，经 `evidence_collector` 脱敏签发标准证据。
4. 若为 `qa` 只读诊断/问答，主图走 `answer_only_node` 依据证据直接输出分析报告并完成任务；若为 `bugfix` / `feature`，则规划变更方案并进入**Linux 容器沙箱子图**，注入 `[REPO_MAP]` 与 `[CHAT_FILES]` 正文生成补丁并运行测试。
5. 测试失败则在沙箱子图内结合报错日志自愈重试，达到上限或测试通过后产出标准 Git Diff。
6. 主图进入人工审批节点挂起，等待用户确认批准或附带意见驳回重写。
7. 审批通过后执行 Git 提交，并将本次报错症状、根因与补丁方案沉淀到 MySQL + ES + Qdrant 报错缓存库，结束任务。

## 4. 代码编辑策略

结合 `aider` 与 `my_swe` 的实践，代码修改与创建统一采用结构化补丁与全仓大纲协同机制：

- **定位与上下文阶段**：使用 `RepoMap`（Tree-sitter AST 符号提取 + PageRank 排序 + Token 二分裁剪）提供 `other_fnames` 骨架，由 `chat_fnames` 承载已读取/待修改文件的完整源码正文（`[CHAT_FILES]`）。
- **修改与创建阶段**：统一采用 `SEARCH/REPLACE` 精确匹配块写入沙箱临时目录（创建全新文件时使用空 `SEARCH` 块），修改后由 AST/语法解析器校验，避免模型计算统一 Diff 行号偏移出错。
- **回滚保障**：修改前校验 Git 工作区状态并记录基线 SHA，审批通过前所有写入均限制在沙箱工作目录内，未批准不污染原分支。
